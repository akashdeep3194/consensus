What is deliberately not here

No Redis yet. It only ever gets derived data — leaderboards, rate limits, caches. Adding it early would invite something authoritative to drift into it.

No Temporal, no Celery. There are roughly four scheduled transitions per round and the database already decides which are legal. A second state machine would be a weaker copy of one that has to exist anyway.

No Docker required. make demo runs a local PostgreSQL cluster under .devdata/.

Types that carry the rules

CREATE DOMAIN prediction_slate AS char(3)
  CHECK (VALUE ~ '^[0-9]{3}$')
  CHECK (-- all three distinct
    substr(VALUE,1,1) <> substr(VALUE,2,1) AND
    substr(VALUE,2,1) <> substr(VALUE,3,1) AND
    substr(VALUE,1,1) <> substr(VALUE,3,1));

"Three distinct digits" is defined once, as a type. Every column using it inherits the rule, so drafts and submissions cannot disagree about what a valid slate is.

Guards that cannot be bypassed

Committed entries are immutable — a trigger rejects any edit to prediction, vote or sequence. Voiding is the one permitted mutation, and it never changes content.

Submissions are append-only — deletes raise, always.

A closed round rejects writes through every path, checked against live round status rather than trusted from the caller.

Illegal transitions raise — legal edges live in a round_transitions table, so adding a phase is data, not a code change.

All 18 of these are exercised by db/tests/constraints_test.sql, which asserts each one rejects for the right reason — a constraint nobody has watched fire is only a comment.

The unit of work

One round, end to end

30 hours from open to reveal, on a 24-hour cadence — so two rounds are always live at once, by design.

T+0 Opendrafts editable · standings public
T+12 Mandatelater locks forfeit Board B
T+23dark
T+24 Sealresolve · reveal at T+30
01
PUT /rounds/{id}/draft
Durable draft write with an optimistic version. Two tabs holding the same version — the second gets a 409, never a silent overwrite. Returns only after Postgres commits.
02
POST /rounds/{id}/lock
One transaction: allocate commit_sequence under an advisory lock, insert the immutable submission, delete the draft. Carries an idempotency key, so a retry after a network failure returns the existing entry rather than creating a second.
03
GET /rounds/{id}/standings
Live vote distribution — the coordination signal the game is built around. Returns nothing at all from blackout onward, rather than something subtly different.
04
seal → SEALING
The atomic cutoff. One small transition establishes it; everything after is resumable, so a worker crash mid-seal is harmless.
05
materialise drafts
Every complete remaining draft auto-commits in chunks, scanned in (updated_at, user_id) order so an auditor replaying the round derives the same sequence numbers we did.
06
SEALING → SEALED + root
Status and Merkle root are written in one UPDATE — a round can never exist sealed-but-uncommitted, and the root can never appear while materialisation is still adding rows.
07
engine.resolve()
The pure function runs over the immutable set: winning number, tiers, both boards, audit ledger. Same code path an independent verifier would use.

The one that actually matters next

Reveal fanout. Every player asks for the result at the same instant, and the global payload — winning number, histogram, audit ledger, root — is identical for all of them. Resolution has a six-hour window to precompute it, so it should be written once as a static object and served from a CDN, with personal result cards precomputed as rows. That turns the hardest scaling problem in the system into one cached file plus cheap keyed reads.
