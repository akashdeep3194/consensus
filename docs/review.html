Design Review · Project Consensus 3D · Ruleset V1.1

The hard problem was
the outcome engine.

A 10-page implementation baseline for a deterministic social prediction game. The persistence architecture was already disciplined. The outcome engine had a degenerate equilibrium — now replaced by a rule simple enough to state in one line, with coordination kept as a core mechanic rather than designed away.

14 findings2 resolved12 decisions settled12 modules · 4 milestones3 open

What holds up

PostgreSQL authoritative with Redis strictly derived, durable acknowledgement only after commit, optimistic draft versioning, idempotent lock-in, and a permanent lower-digit tie-break. Sections 4–6 are close to build-ready. The reasoning in §4.2 for rejecting a Redis-first write path is exactly right.

What still needs work

Twelve implementation findings stand, two of them blocking: the load target is aimed at the wrong phase, and the Merkle commitment is published too late to prove anything. Neither needs a decision — both have agreed approaches. The real gap is that no code exists yet.

Resolved

The outcome engine, replaced

D'Hondt allocation collapsed to a repeated digit whenever any bloc passed 25% of the vote — and since joining the visible leader cost a player nothing, the game drifted there on its own. Ranking distinct digits removes that failure mode structurally.

F1  ·  RESOLVED IN RULESET V1.1

The winning number is now the three most-voted digits, ranked

The whole engine

counts[d] = committed vote count for digit d
winning_number = first three of
    sort(digits 0–9) by (count descending, digit ascending)

Integer comparison. No quotients, no division, no rational arithmetic, no float-drift risk — the v2.1 requirement for exact Fraction math (§2.2) disappears entirely, and with it a whole class of test. Ties resolve to the lower digit at every position, which is the only tie-break in the system.

Zero votes need no special case. Every count is 0, so every comparison ties and the lower digits win in order: the result is 012.

Distinct a repdigit is no longer representable
720 ordered outcomes, down from 1000
Ranked position encodes vote order
Simpler a sort, not an allocation algorithm

What coordination actually buys

Organising blocs is now intended gameplay, and the standings stay public so they can be played against. The rules make that safe to permit — a bandwagon no longer collapses the game, it only claims one position.

One bandwagon — the natural, self-reinforcing behaviour that broke D'Hondt — now locks only position 1 and leaves 72 outcomes live. That is where most rounds will sit, and it is the interesting case: visible partial control, with a real prediction problem left over.

Fully solving the number takes three separately organised blocs holding deliberately different sizes, in public, for 23 hours. That is an achievement rather than an accident — and it is contestable, because the standings are visible to everyone and only a modest fourth bloc breaks the ordering.

Residual risk — watch, don't fix

The three-bloc lock is still reachable

It is far harder to reach than a bandwagon and arguably a legitimate play. Two things keep it honest: the lock is visible for 23 hours, so it invites disruption; and the blackout hour is the one window where it cannot be verified before sealing — which makes the blackout load-bearing game design now, not just an information-policy detail.

Track it in production: alert when the live outcome space falls below ~10 possibilities before blackout. A game-health metric, not a bug.

Settled

Two boards

Digit distance is retired. Under V1.1 a digit is a faction identity, not a magnitude — digit 4 is not "nearly" digit 5, it is a different bloc that lost. Scoring on numeric adjacency measured something the game no longer models.

SCORING MODEL  ·  RULESET V1.1 §3

One board for calling the result, one for reading the electorate

Board A

The Number

Who called the outcome. This is where the prize sits. Borrowed vocabulary: in racing a trifecta is the top three in exact order, and a boxed trifecta is the same three in any order — precisely this structure, so the words arrive already meaning the right thing.

TierConditionat 500k
🏆 TRIFECTAthree digits, exact order~694
📦 BOXEDthree digits, any order~3,472
TWOtwo of three—
ONEone of three—

Every player in a tier shares it. No intra-tier ranking, no timestamp tie-break — if 694 players hit the Trifecta, all 694 win it.

Board B

The Mandate

Who read the electorate, ranked by a position-weighted vote total.

mandate_score(P) =
  3·C[P₁] + 2·C[P₂] + 1·C[P₃]

Its unique maximum is the Trifecta — by the rearrangement inequality, pairing the largest count with the largest weight is optimal, so the top of this board is always the true number in exact order.

Misordering costs exactly the margin you misread. Swapping two positions costs the gap between those digits' vote counts, so misreading a near-tie barely hurts and misreading a landslide hurts a lot. The penalty is proportional to how hard the call actually was — something digit distance could never express.

Why weighted, and why gated

Problem with the raw ideaEvidenceFix
Unweighted summation is order-blind Collapses to 120 tiers — one per digit set — so ~4,000 players tie per rank Weight 3/2/1 → ~670 of 720 ranks
The answer is published live A player copying the standings before blackout scores 99.99% of maximum, beaten by ~1 prediction in 720 Only entries locked before T+12h score on this board

The eligibility gate repairs something already broken. Under v2.1 manual lock-in is strategically pointless — auto-commit at seal performs the identical transition, so no rational player ever locks early. Mandate eligibility gives early commitment a purpose and creates the game's first real risk/reward decision: lock early to compete on the Mandate board and lose the ability to react, or stay flexible and chase the Trifecta.

An early lock carries genuine risk — the slate leading at T+12h keeps the same three digits only 18–46% of the time, and the exact order as little as 5.5%.

Why two boards, not one ranking

The metrics genuinely disagree

For a winner of 738 with counts 7:175,000 · 3:125,000 · 8:25,000, 49 predictions holding only two of the three winning digits outscore the worst BOXED permutation. A single merged ranking would place a partial hit above a player who had every winning digit — indefensible. They measure different things and must be reported separately.

What the player sees. Board B ranks by weighted score, but displays the interpretable number: "your slate commanded 51.1% of the vote." Well-defined every round — ~30% for everyone when nobody organised, up to ~73% for the winning slate under heavy coordination.

Findings

The implementation twelve

Unchanged by the rule change. Graded by what happens if they are left alone.

F2
Blocking

The load target is aimed at the wrong phase

§9.1 targets 500k concurrent submissions in the last 10 minutes — but drafts are durable for 24h and seal auto-commits every valid one. The design already engineered that spike away. The real wall is reveal fanout at T+30h, a read problem needing a completely different solution.

FixBenchmark three separate profiles: draft writes, the sealing batch, and 500k-concurrent reveal reads.
F3
Blocking

A Merkle root published at reveal proves nothing

§8.3 discloses the commitment at T+30h, but it is computed at seal and the operator controls both the data and the clock. A root revealed alongside the result it commits to is decorative.

FixPublish at T+24h on seal, to an append-only location the operator cannot rewrite. Note a leaf is now brute-forceable in 7,200 guesses — fine if entries are public, but decide it.
F4
Important

Merkle reproducibility rests on an unspecified ordering

Leaves hash "in commit order". For up to 500k drafts auto-committed at seal, that is whatever order the batch job inserted rows — not reproducible by an auditor, not stable across a crash. This breaks acceptance criterion §9.4 directly.

FixMake seal-time commit_sequence a specified deterministic function of the data, e.g. ordered by (updated_at, user_id).
F5
Important

"Atomically finalize all drafts" contradicts "restartable"

§5.3 asks for both across up to 500k rows. One transaction gives atomicity but no partial restart; chunked commits give restart but not atomicity.

FixThe atomic moment is the status transition, not the data movement. Flip OPEN→SEALING in one small transaction to establish the cutoff, then run idempotent chunked inserts, reconcile counts, and only then mark SEALED.
F6
Important

"Valid remaining draft" was undefined — and it moves the tally

A draft with a prediction but no vote is reachable, and whether it commits changes the counts and therefore the winning number. The §4.3 schema declared no NOT NULL and no CHECK.

SettledBoth fields required, enforced in the schema rather than only the API, with invalid drafts discarded at seal and counted in the audit record.
F7
Important

Rounds overlap, and nothing acknowledges it

24h entry + 6h resolution = 30 hours. On a daily cadence, round N is still resolving six hours into round N+1. That makes /rounds/current ambiguous and means a player legitimately holds a committed entry in one round and a draft in another.

FixPick the cadence explicitly, and scope the one-entry invariant per round rather than globally.
F9
Important

No identity model exists — and it now defines the boundary of fair play

Raised from "decide" by the rule change. Now that organising a voting bloc is legitimate, encouraged gameplay, the only thing separating a real coalition from one person running 10,000 accounts is the identity model — and none is specified. Permitting coordination makes sybil resistance more load-bearing, not less.

FixOAuth only, one account per verified provider identity, Turnstile, registration rate limits, and an anomaly path that voids entries as data so the resolver stays pure.
F8
Decide

Blackout has a side channel — and now carries real weight

Every aggregate endpoint must return the identical frozen snapshot — same bytes, same ETag — or size and timing leak state. The second half is now answered by design: the snapshot advantages organised blocs, and that is intended. The dark hour is what keeps a multi-bloc lock contestable.

F10
Decide

/leaderboard cannot exist during a round

Predictions are unrankable before the winning number exists, so during OPEN the "leaderboard" can only be the vote distribution. That is now the game's central public signal rather than something to hide — but the name still misleads.

FixSplit into /standings (live vote distribution) and /results (post-reveal rankings).
F11
Decide

Redis-outage policy for rate limits is unstated

Rate limits live in Redis. On outage, does the API fail open and risk a bot flood, or fail closed and stop the game? Recommend fail open with a loud alarm — Turnstile and the unique-entry constraint still hold.

F12
Decide

The API surface is missing its non-game half

Absent from §7.2: authentication, profile and history, round listing, server time (the console must never trust a client clock), health, an operator surface for inspecting transitions, and any push channel for reveal.

F13
Decide

No retention loop is defined

The document specifies a correct round but never says what a win is — no prize, score, streak, rank or season. More tractable now: with 720 outcomes and a real prediction problem left after coordination, exact winners are genuinely rare, so a reward can mean something.

Implementation layer

Stack

The v2.1 stack is sound. Two choices are worth arguing with, and several layers were never specified at all.

Disagreement 1

Temporal is the wrong tool for V1 orchestration

There are roughly four scheduled transitions per round, and §6.1 already insists the database — not an application timer — is authoritative for whether a transition is legal.

Temporal would run a second, weaker copy of a state machine that must live in Postgres anyway, paying a cluster and a new failure domain to schedule four timers. Use a Postgres-backed scheduler with advisory locks: a few hundred lines, no new infrastructure, one state machine. Adopt Temporal when resolution grows external calls — the migration is easy precisely because transitions are already idempotent.

Disagreement 2

The resolver must be its own dependency-free package

Not in the document, but it is what makes acceptance criterion §9.4 achievable rather than aspirational. The API imports it, the sealing worker imports it, and the public audit CLI imports it and nothing else.

Under V1.1 it is also tiny — a sort plus a distance function — and the only part of the system that can be exhaustively tested: all 720,000 prediction/winner pairs, plus property tests over count vectors, plus frozen golden vectors that fail loudly if behaviour changes without an algorithm_version bump.

The part with no design yet

Reveal fanout at T+30h

Resolution has a six-hour window before reveal, so almost nothing needs to be live. The global payload — winning number, histogram, audit ledger, Merkle root — is identical for every player: write it once during resolution as a static immutable object and publish it to the CDN at exactly T+30. One object serves 500k clients at zero database cost.

Precompute every personal result card as a row during resolution, so reveal is one indexed keyed read with no computation and no join. Then have clients poll with server-directed jitter spread over ~60s — never let 500k clients fire at once because their own clocks said so. That turns the hardest scaling problem in the system into one CDN object plus cheap keyed reads.
